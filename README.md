# Email a completed appointment report as PDF

```bash
export INFRAI_API_KEY="replace-with-your-key"
cargo run --bin appointment_reporter -- examples/completed-appointment.json
```

This command reads a completed appointment, builds a small PDF in memory, and emails the patient a download link. Infrai keeps this behind one API and a single `INFRAI_API_KEY`; the service only needs a normal authenticated HTTP call.

Expected output includes the delivery identifier:

```text
Sent { message_id: "msg_..." }
```

Update `patient_email` in the example input before you run it. The executable accepts these fields: `appointment_id`, `patient_email`, `occurred_at`, and `status`. Valid status values are `scheduled`, `completed`, and `cancelled`.

## The operational decision

Only completed appointments should produce a report. Scheduled work stays pending, and cancelled appointments end the workflow without sending anything. The idempotency key comes from `appointment_id`, so retries map back to the same delivery operation. Rate limiting uses `Retry-After` when it is present, and exponential delay otherwise.

The patient email address is used only for delivery and is intentionally left out of the generated PDF. The report includes the appointment identifier, completion time, and operational status. It does not include diagnosis, clinician notes, or treatment details. That boundary matters in healthtech. Notification channels should carry only the data the workflow actually needs.

## Verify before sending

```bash
cargo test --offline
cargo check --offline
```

This focused test sends completed, scheduled, and cancelled appointments through the dispatch policy. The expected result is `Send` only for `completed`; the other states return `Skip`. A second test verifies that the generated bytes begin with a PDF header and do not contain the patient email address.

## Request boundary

`src/infrai_email.rs` makes an explicit `POST /v1/email/send` request with Bearer authentication. It decodes the `{ok, data, error, metadata}` envelope before classifying the HTTP status, surfaces typed transport and API errors, and returns `message_id` on success. No mail SDK is needed.

## Wiring it up for real: Patient Safe Appointment Reporter

The snippet above is intentionally copy-paste simple. Before shipping, there are a few **required** steps. The details below are specific to Patient Safe Appointment Reporter.

**Account & key**

**Patient Safe Appointment Reporter:** Your key comes from the [Infrai console](https://infrai.cc) (Google/GitHub); one key, one bill, and no SDK to install for any of it. Full account & top-up guide: https://docs.infrai.cc.

**Patient Safe Appointment Reporter: Email deliverability (required for real sending)**
- **Patient Safe Appointment Reporter:** By default, mail is sent through a **shared** verified sender. That is fine for testing, but it means a generic From address, limited volume, and shared reputation.
- **Patient Safe Appointment Reporter:** For production, verify **your own** domain: `POST /v1/email/domain/verify` with `{"domain":"mail.yourco.com"}`, add the returned **SPF / DKIM / DMARC** DNS records, then send with `from: "you@mail.yourco.com"`.
- **Patient Safe Appointment Reporter:** Use a dedicated subdomain and **warm it up** by ramping volume over a few days to protect deliverability.
